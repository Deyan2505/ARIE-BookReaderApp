# Phase 0A — Lossless Reader Pagination Recovery

> Създаден: 2026-07-19. Read-only диагностика — никакъв код не е променян.
> Дефектът е БЛОКИРАЩ: Phase 1+ (auth, upload) не започват преди Phase 0A да мине QA.

---

## 1. Дефектът с едно изречение

Сървърът реже книгата на ~1200-знакови chunk-а на сляпо (`paginateText()`,
`netlify/functions/api.js:83-124`), а четецът рисува от всеки chunk само колкото се
побере на canvas-а и **мълчаливо изхвърля остатъка** (`wrapText()`,
`public/js/reader.js:428-458` — спира при `maxY`, не връща остатък; никой не го пренася).

## 2. Доказателства (реалната книга, 2026-07-19)

### Сървърен слой — оневинен

### Преходът страница 6 → 7 (screenshot доказателство, стойности измерени)
- Chunk 6 (1047 зн.) реално завършва с «…„днес“ вече е мъртво.»
- На екрана (canvas 439×557, шрифт 20) стр. 6 завършва с «…за да не се разпадне.» —
  симулацията предсказа точно това (`lastDrawnTail: "разпадне."`), потвърдено визуално.
- Първият изгубен ред: «— Просто е дълъг д…» — **682 знака диалог никога не се показват**.
- Стр. 7 започва с «Марк излезе от стаята,…» — различен следващ абзац, точно както в
  доклада на автора. (Неговият cutoff „За…“ е същият механизъм при неговия viewport —
  вътре в chunk 6 има точно едно самостоятелно „За“.)
- Дублиране НЯМА: сървърните диапазони не се припокриват, клиентът никога не преизползва
  остатък. Загубата е еднопосочна.

### Второстепенни дефекти, открити покрай това
1. `trim()` в `paginateText` унищожава празните редове на всяка chunk граница (731 зн.).
2. Race condition: `loadPageContent()` няма in-flight guard — бързо прелистване = конкурентни
   fetch-ове с преплитащ се state.
3. При голям шрифт последният ред може да се committed на y≈maxY и глифовете да навлязат
   в зоната на footer-а (footer е на height−32, maxY е height−50).
4. Resize/fullscreen само прерисува същия chunk → размерът на загубата се променя тихо.
5. `styles.css:1` зарежда 'Lora'/'Outfit' през @import; първото рисуване може да стане
   преди шрифтът да е зареден; няма re-render на `document.fonts.ready`.
6. Индикаторът „Страница X от 232“ брои API chunk-ове, не реални визуални страници.

## 3. Архитектурен избор

| | A. Client-side visual pagination (пълен логически буфер) | B. Streaming chunks + overflow carry | C. Server-side layout-aware пагинация |
|---|---|---|---|
| Lossless | ✅ по конструкция ([start,end) диапазони) | ✅ напред; ⚠ назад/скок — anchor-зависими граници | ⚠ зависи от шрифтов паритет server/browser |
| Общ брой страници | ✅ точен | ❌ неизвестен без пълен layout | ✅ |
| Прелистване назад / скок по progress bar | ✅ мигновено, детерминистично | ❌ ill-defined (обратен layout) | ✅ |
| Мрежа | ~350 KB веднъж на сесия (по-малко от корицата 2.4 MB); нула при прелистване | минимална | пер-device кеш експлозия |
| „Измервай със същия ctx, с който рисуваш“ | ✅ | ✅ | ❌ node-canvas ≠ browser rasterizer |
| Presъдa | **ИЗБРАНА** | механизмът ѝ (exact remainder) се ползва ВЪТРЕ в layout pass-а на A | Отхвърлена |

**Решение:** A — клиентски layout engine върху пълния декриптиран буфер (batch fetch на
криптираните chunk-ове), детерминистична глобална пагинация при текущите метрики,
offset-базиран прогрес. XOR транспортната защита, Canvas rendering и визуалната
идентичност остават непроменени.

## 4. Дизайн на layout engine (изисквания → механизъм)

- Измерване със **същия** canvas ctx и същия font string, който рисува; layout стартира
  след `document.fonts.ready`.
- Изход: `pages: [{start, end, lines:[{text, y}]}]` — точното съдържание + точният
  остатък; `renderCanvas()` само рисува готовите линии (без повторен wrap → нулев шанс
  за разминаване measure/draw).
- Разделяне: граница на абзац → край на изречение → интервал → символен fallback само
  при дума, по-широка от maxWidth. Празни редове и абзацна структура се запазват.
  Кирилица/дълги тирета/кавички: measureText е глифово-точен, fixtures в тестовете.
- Репагинация само при промяна на метриките (fontSize, canvas W/H, dpr, orientation,
  fullscreen) — сигнатурно сравнение, debounce, loading state върху canvas-а,
  layout version token срещу race; при обикновено прерисуване — нула репагинация.
- Навигация: индекс в масива pages, без мрежа, in-flight guard, бутоните неактивни
  по време на relayout.

## 5. Сървърни промени (минимални, без XOR промени)

1. `paginateText()`: премахване на `.trim()` и empty-филтъра → chunk-овете стават точни
   непрекъснати подниза (byte-exact conservation). Ефект върху стар клиент: козметичен.
2. `/api/books/:id/read`: + `totalChars`, + `chunkSizes[]` (за offset аритметика и миграция).
3. Нов `GET /api/books/:id/chunks?from=&to=` — batch криптирани chunk-ове (същият
   per-book XOR ключ), валидиран диапазон. `/page/:num` остава за съвместимост.

## 6. Прогрес — нов модел и миграция

Ключът остава `arie_p_<bookId>`. Нова схема:
`{ v:2, off:<абсолютен знаков offset на началото на текущата визуална страница>,
   pct, page:<chunk индекс за rollback съвместимост>, total:232, ts, lv:<layout сигнатура> }`

- `off` е layout-НЕзависим → resize/шрифт/устройство връщат читателя на същото изречение
  (страницата, чийто диапазон съдържа off). Никакво връщане в началото.
- Миграция (еднократна, при първо зареждане): старо `{page:N, total}` →
  `off = Σ chunkSizes[0..N-3]` (стар визуален номер == API chunk; N=1/cover → off=0). Точна.
- Rollback съвместимост: полето `page` продължава да се пише като chunk индекс, който
  съдържа off → стар клиент чете прогреса смислено.
- Прогресът на различните книги остава разделен (per-key, непроменено).

## 8. QA матрица

Автоматично: 6 viewport-а × 11 шрифта × инварианти (Tests 2–4) + Node Test 1 + fixtures
(Test 7). Ръчно/визуално: последният ред не е отрязан; текст не влиза под footer/рамка;

mobile библиотека + четец; регресия: съществуващи екрани, защити, прогрес на 2 книги.

## 9. Рискове и rollback

- Layout време на слаби телефони → word-width кеш + async pass + loading state (цел <800ms).
- Batch размер при бавна мрежа → loading state; бъдещо range-батчване е предвидено в API.
- `document.fonts.ready` забавяне → loading state, не грешен layout.
- Динамичен общ брой страници → честен per-device брой; % и off пазят непрекъснатост.
- Rollback: един branch/commit revert; API промените са адитивни (стар клиент работи);
  Netlify instant rollback към предишен deploy; progress v2 е обратно четим.
